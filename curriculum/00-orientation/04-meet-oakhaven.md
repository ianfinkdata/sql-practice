## The company

Oakhaven is a fictional outdoor-gear retailer: think hiking boots,
tents, climbing chalk, ski jackets, water bottles. It sells through two
channels — online and in physical stores — has a roster of employees
across sales, support, warehouse, and management, and has accumulated
several years of order history from a customer base spread across the
US.

None of that is real. But the *database* behind it is real, sitting
right here at `project/oakhaven.db`, generated by a script with a fixed
random seed so it's the same every time you build it. Every number and
example in this course comes from actually querying that file — not
invented, not approximated.

Oakhaven is deliberately small enough to hold in your head: five raw
tables, a few hundred to a few thousand rows each. Small enough that
you can `SELECT *` a whole table and skim it, but large enough that
"just look at it" stops being a substitute for actually writing SQL.
That's exactly the size where SQL starts paying for itself.

## The five bronze tables, at a glance

"Bronze" is a name you'll see a lot — more on that in a moment. For
now, just think of it as: **the raw tables, as originally recorded.**
There are five:

| Table | What it holds |
|---|---|
| `bronze_customers` | One row per customer: name, contact info, state, signup date, account status, and customer segment (Retail/Wholesale/VIP). |
| `bronze_products` | One row per product Oakhaven sells: name, category, brand, cost, price, and a SKU code. |
| `bronze_employees` | One row per employee: name, department, region, hire date, and whether they're a manager. |
| `bronze_sales` | One row per **order line** — the transactional heart of the database. Each row is one product sold on one order: quantity, price at time of sale, discount, payment method, and more. |
| `bronze_calendar` | One row per calendar date, from 2018 through 2038. Not "messy" like the others — it's a manufactured reference table used for date-based reporting later in the course. |

Notice the sizes are wildly different: ~600 customers, ~150 products,
~35 employees, but **12,000** rows of sales — because every customer
can place many orders, and every order can have multiple line items.
That's normal: transactional tables are almost always the biggest
table in a retail-style database, and it's why so many SQL questions
in the real world end up centering on a table like `bronze_sales`.

## A first look

Let's actually look. Run these — either at the `sqlite3` prompt or in
DB Browser's query editor.

### Try it: peek at customers

```sql
SELECT * FROM bronze_customers LIMIT 5;
```

Real output from this database:

| customer_id | first_name | last_name | email | phone | state | signup_date | is_active | customer_segment |

| 1 | michael | cantu | michael.cantu@outlook.com |  | NJ | 2022-06-26 19:12:42 | yes | Retail |
| 2 | Ricardo | Brooks | ricardo.brooks@yahoo.com | 4278193651 | ar | 12/01/2018 | yes |  |
| 3 | Kevin | potter | kevin.potter@outlook.com | +1 363 326 9140 | co | 01/14/2022 | true | VIP |
| 4 | Rachel | Gomez | rachel.gomez@oakmail.com | (941) 660-5364 | Idaho | 2025-02-22 | 1 | retail |
| 5 | John | harris | john.harris@yahoo.com | 472-676-3094 | virginia | 09/09/2018 | true | Wholesale |

Take a second and actually look at that output. `first_name` casing is
inconsistent (`michael`, `Ricardo`, `Kevin`). `phone` shows up in at
least three different formats in five rows. `state` mixes abbreviations
(`NJ`, `ar`, `co`) with full names (`Idaho`, `virginia`) — and note the
casing isn't even consistent within a format (`ar` and `co` are
lowercase abbreviations; `NJ` isn't). `is_active` is text, not a clean
true/false, and it's not even consistently spelled (`yes`, `true`,
`1`). Customer 2's `customer_segment` is blank.

This is not a mistake in the database — **it's the point.** Real-world
raw data looks exactly like this: inconsistent, occasionally missing,
never quite what a tidy diagram promises. You'll spend Tier 1 learning
the tools to work with data like this, and Tier 2 specifically learning
how to clean it up.

### Try it: how many rows are we working with?

```sql
SELECT COUNT(*) FROM bronze_customers;
SELECT COUNT(*) FROM bronze_products;
SELECT COUNT(*) FROM bronze_employees;
SELECT COUNT(*) FROM bronze_sales;
SELECT COUNT(*) FROM bronze_calendar;
```

Real output: `600`, `150`, `35`, `12000`, `7670`, in that order —
you'll use `COUNT(*)` for real in Tier 1's aggregates module; for now
it's just a fast way to confirm your build matches everyone else's.

## A first preview: bronze, silver, gold

You'll hear these three words constantly through this course, so
here's the plain-English version now, without any SQL attached yet.

This pattern is called a **medallion architecture**, and it's a common
way real companies organize a data pipeline into layers of increasing
trust and polish:

- **Bronze** — raw, as-received data. Messy on purpose: inconsistent
  casing, missing values, mixed date formats, even outright bad data
  like negative costs or orphaned foreign keys. This is what you just
  looked at. Nobody "fixes" bronze — it's meant to preserve exactly
  what came in, mess and all, so nothing is silently lost or
  misrepresented.
- **Silver** — cleaned and standardized. Same information, but names
  are consistently cased, dates are parsed into one format, messy
  boolean text becomes real 0/1, and known data-entry bugs (like a
  discount stored as `25` instead of `0.25`) get corrected. You'll meet
  this layer starting in Tier 2.
- **Gold** — business-ready. Reshaped for actual reporting and
  analysis: renamed into business-friendly terms, joined together,
  sometimes pre-aggregated (e.g. "total sales by month and category").
  This is what a dashboard or report would actually query. You'll meet
  this layer in later tiers.

Every table you looked at above (`bronze_customers`, `bronze_products`,
`bronze_employees`, `bronze_sales`, `bronze_calendar`) is bronze. The
whole rest of this course is, in a sense, the story of turning these
five raw tables into something trustworthy and useful — one SQL
concept at a time. You don't need to remember any of the
bronze/silver/gold details yet; just file away that the mess you saw
above is intentional, and there's a plan for it.

## Key takeaways

- Oakhaven is a small, fictional outdoor-gear retailer with five raw
  ("bronze") tables: `bronze_customers`, `bronze_products`,
  `bronze_employees`, `bronze_sales`, `bronze_calendar`.
- `bronze_sales` is the biggest table (12,000 rows) and the
  transactional core — one row per order line, not per order.
- Bronze data is intentionally messy — inconsistent casing, mixed
  formats, missing values — because that's what real raw data looks
  like.
- **Bronze → silver → gold** is a medallion architecture: raw → cleaned
  → business-ready. This whole course is organized around that one
  pipeline, applied to this one small database.
